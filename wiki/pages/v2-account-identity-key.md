# v2 account identity key

**Status: per [`docs/protocol.md`](../../docs/protocol.md) rev 2.1, §4.1, §4.4, §8, §9; implemented as of 2026-11-13**
(server: `services/identity.py`; app: `src/core/crypto`, `src/core/trust/deviceDirectory.ts`, `src/core/session`).

## Context

Rev 1 trusted every device the server listed for a user (per-device TOFU). A malicious server, or anyone with the
user's password (each login creates a device), could add a device and silently receive all future messages.

## Choice

- **AIK**: one Ed25519 key per account, generated by the first device. Public half in `users.identity_key`; secret half
  only in linked devices' secure storage and inside a [link transfer](v2-history-transfer-and-backups.md).
- **Device certificate**: `Ed25519.sign(AIK_secret, "fixes/v1/device-cert|" + user_id + "|" + device_id + "|" + public_key_b64)`.
  The server verifies it against `users.identity_key` before storing; clients verify again against their pinned AIK.
  A device is **linked** once certified; only linked devices are encrypted to or accepted from.
- **Linking**: the first device self-certifies (`PUT /v1/users/me/identity`); a re-login on a phone that still holds
  the AIK secret self-certifies too; any other device must be certified by scanning its QR on a linked device. A
  password alone never grants access to messages.
- **Reset identity** (`POST /v1/auth/reset-identity`, needs the password): for a user who lost every linked device.
  Revokes all other devices and replaces the AIK. The app stores the new AIK before the call; a definitive rejection
  restores the old one, while a lost response (network error) keeps it and schedules a quiet link-state re-check
  (`SessionManager.resetIdentity`), since the `devices_changed` of an applied reset may never arrive. Before round 2
  the phone stayed stuck on "Link this device". A retry after a lost response reuses that pending key
  (`pendingResetIdentity`), so a repeated tap never rotates the account key twice (fixed in code-review round 3).
- **Pinning**: the app pins each contact's AIK on first use (`contact_identities`). A changed AIK is held as
  `pending_identity_key`, a system message is inserted, and **sending to that contact is blocked** until the user taps
  Accept. Safety code = SHA-256 over both AIKs in byte order, 12 groups of 5 digits, identical for both users. Your own
  side must be the AIK held on the phone, never the server's copy
  ([gotcha](safety-code-from-local-identity-key.md)).
- **Own devices** are judged only under the AIK held on this install, in linking mode too; the server's account key
  is trusted only by a fresh install that holds none (`ownIdentityKeys()` in `src/core/messaging/runtime.ts`, as of
  2026-11-13). If the two differ, a device certified only under the server's key may still deliver the `link`
  transfer (checked against that key and authenticated by the QR secret, §7.3) but never sync copies or read syncs,
  since the server could have made its certificate. Before code-review round 2 the app trusted the server's key in
  linking mode even when the phone held a different one.
- Unexpected own devices appear as "Not linked" (certificate does not verify under the AIK on this phone) on the
  Devices screen, flagged "NEW" when added after this device within 7 days, and can be revoked there.

## Rejected

- **Versioned signed device list**: more complex. Per-device certificates also let receivers verify envelopes from a
  device revoked while they were in flight (a revoked device is accepted only for envelopes created before
  `revoked_at`).

## Residual risk

A malicious server colluding with whoever holds a revoked device's secret key can keep that device receiving, since
the server is the one that reports revocation.
